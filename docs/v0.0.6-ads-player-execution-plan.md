# v0.0.6 广告稳定性与播放器改造执行方案

> 状态：截至 2026-11-10，v0.0.6 API 已在 DramaFlicks 路径做生产 canary，五库迁移与候选镜像预检通过；这不是 Mini ZIP 发布完成。TikTok Portal 核位、iOS/Android 真机和 DramaFlicks 旧包完整业务冒烟仍未验收。实际状态见第 10 节；编制日期：2026-11-09。

## 1. 目标、范围与结论

v0.0.6 要同时解决三件事：减少可由客户端控制的广告重复展示和错误放大；找出 iOS `show()` 环境检查高失败率的真实触发条件；让剧集首播、切集和广告返回后的播放器稳定可观测。**不能承诺仅靠更换广告位或后端改动消除 TikTok 原生环境错误。**

首批以 HeartReel、SweetReel、LuxeReel、DramaFlicks 四包做同包灰度；ZenClip 可复用现有埋点接口，在确认基线后加入。共享 `apps/mini-web` 代码还服务其他小程序，特别是带 `v005App` 分支的 BloomReel、QuillShort、AmberPlay、NimbusClip、RuneReel；所有新行为必须按 `appKey + releaseId` 显式启用，不能因共享代码更新而改变旧包。活动链接免费集直达仍须沿用现有入口豁免逻辑。

上线初始策略：**剧集解锁激励保留；自动入口广告与定时插屏对 v0.0.6 新 release 默认关闭**，待真机验证后按 release 打开。插屏仅考虑自然切集后的过渡点，不在播放中打断视频。已保存的旧 release 策略不做批量覆盖。

### 现有证据和不能下的结论

附件《已粘贴的文本.txt》统计北京时间 **2026-11-08 00:00 至 2026-11-09 08:00** 的入库事件：失败/超时共 271,273 条；其中 iOS `101150000 / subErrorCode=50008 / env check failed` 233,806 条，占 86.2%；`11006/104111006` 重复展示 23,517 条。约 99.3% 的 iOS 环境错误在 `show()` 后 100 毫秒内返回；四库 `metadata.sdkCallback` 入库数均为 0。这里的分母是**事件次数**，不是失败用户数或独立展示次数。HeartReel、SweetReel、LuxeReel 的 iOS 展示失败/超时事件比例分别为 88.9%、92.4%、94.7%，DramaFlicks 为 12.2%；四包 iOS 都有成功展示。详见附件及 `outputs/client-analytics-20261108-09-20261109/` 的汇总与四份明细。

| 观察 | 当前判断 | v0.0.6 要验证什么 |
| --- | --- | --- |
| `50008` 极快返回且集中于 iOS `ad_show` | 更像原生展示资格/容器状态检查；与显式 `load()` 路径高度相关，**因果未证实** | 同一包、同一广告位、相近 TikTok 版本，对比显式 `load()` 与新实例直接 `show()`；同时记录前后台及实例时序。 |
| `11006` 重复展示量高 | 全局互斥、关闭回调与原生释放的时序仍有缺口；也可能是多个业务触发器竞态 | 一次只允许一个原生广告进入展示状态，确认 `onClose/onError/show()` 乱序和切页场景。 |
| `Client Key is not match` 消息 466 条，但子码多数为 `20001` | 服务端配置、客户端广告位和 Client Key 哈希的只读核查未发现持续串包；同广告位 Android 有成功记录 | 到 TikTok Portal 逐包核对主备广告位归属、状态；保留原始码/子码/消息，向平台提交冲突样本。 |
| `sdkCallback` 入库为 0，客户端版本缺失较多 | 当前源码有回调采集及 `metadata` 入库路径，但不能据此证明统计期线上包已运行该代码 | 以发布包 `releaseId`/ZIP SHA、调试台单条记录、`/analytics/events` 响应和数据库行做端到端核对。 |

Mini Games 错误码表将类似 `env check failed` 文案列在另一子码下，不能把它作为 Mini Drama 的精确定义。保留 SDK 实际返回的 `error_code`、`sub_error_code`、`error_msg`、回调来源和脱敏原对象，避免把应用自定义的 `AD_SHOW_TIMEOUT`、`AD_CLOSE_TIMEOUT`、API HTTP 状态混称为“官方错误”。`onClose.isEnded=false` 也不能一律标成用户主动取消，播放错误可能伴随关闭回调。

## 2. 实施前调用链与主要缺口（基线）

```text
启动/进集 -> 匿名会话与策略/奖励会话 -> 按 placementId 预建实例
  -> 若运行时有 load() 则显式调用并最多等 8 秒 -> show()
  -> show Promise / onError / onClose -> /ad-events -> /shown 或 /complete
  -> 下一条激励或恢复/切换剧集
```

1. `ad-instance-cache.ts` 按广告位各缓存最多两个实例；`app-entry-ad.ts`、`rewarded-ad.ts`、`episode-interstitial.ts` 都可能提前 `load()`。当前未区分 iOS/Android，且“两广告位 × 两实例 × 多广告类型”会把并发准备量放大。
2. `ad-activity.ts` 只有内存布尔互斥。入口、解锁、退出挽留和插屏虽然调用它，但 `onClose` 后立即释放与下一条 `show()` 可能只隔几十毫秒；原生层是否完全释放不可见。超时后也不能立刻推断原生广告已经关闭。
3. 入口 `SHOWN` 模式 `/shown` 以有序计数推进，但现接口没有实际广告位参数，也不要求先有一条持久 `SHOWN` 事件；双位后须补证据链。剧集奖励和入口 `COMPLETED` 模式则在 `/ad-events`、`/complete` 中对单一会话 `placementId` 做等值校验，前端单独改为备用位会得到 409。
4. `WatchPage.tsx` 对部分 v0.0.5 包在 `playbackActive` 时启动定时插屏调度；默认策略源码里 `episodeInterstitialEnabled=true`，不能仅凭入口 `enabled=false` 推断插屏关闭。需逐 release 查询实际保存策略。
5. 播放器已使用 `TTMinis.getPlayer('byteplus')`、`playNext()`、`prefetchMediaInfo()` 和 `setPreloadList()`。`drama-player-controller.ts` 对同一批源同时发起 `prefetchMediaInfo` 和 `setPreloadList`，预取失败被吞掉；切集/首帧失败很难区分是播放授权、预加载、SDK 初始化、自动播放还是媒体本身。`PlayerShell.tsx` 的首帧近似用正数 `TIME_UPDATE`，应单独记录“可播放/开始播放/首个有效画面”的可观测阶段。

## 3. 广告运行规则

### 3.1 平台策略和实例生命周期

官方 Mini Drama 广告流程提供创建、`onError`、`onClose`、`show()`，强调每次展示使用新实例；当前文档**没有承诺显式 `load()/onLoad` 是所有 Mini Drama 客户端的通用必需流程**。以下 iOS/Android 分流是基于本项目数据的待验证产品策略，不是声称 TikTok 官方要求两个系统用不同 API。

| 平台/阶段 | v0.0.6 初始规则 |
| --- | --- |
| iOS | 当前默认保留 `EXPLICIT_LOAD` 对照策略；仅在后台启用合法主备配对并设置 iOS 实验比例后，部分请求使用新实例 `DIRECT_SHOW`。页面可见与 Mini `minis.show` 事件用于时机控制；不得把固定延时当作环境可用证明。 |
| Android | 可在已知业务意图/会话时预建当前激励或插屏实例，并仅在 SDK 实际提供 `load()` 时加载；全局最多一个当前实例和一个下一实例，不同时预热主备位。 |
| 未识别平台或 SDK 能力缺失 | 新实例直接展示或按业务降级；无 `load()` 时埋点为 `unsupported`，不是加载失败。 |
| 所有平台 | `canIUse`、前台状态、同一展示操作唯一 `operationId`、全局互斥；实例只 `show()` 一次。每个监听器在终态解绑；只在 SDK 提供 `destroy()` 时调用。 |

统一状态机：`IDLE -> WAIT_FOREGROUND -> CREATING -> [LOADING] -> SHOW_CALLED -> SHOW_ACCEPTED -> CLOSE_RECEIVED -> NATIVE_COOLDOWN -> IDLE`；`onError`、Promise reject、应用超时各走独立失败终态。`onClose` 可能早于 `show()` Promise 落定，按一次操作的状态合并，不重复记成功、失败或发奖。关闭/报错后维持短暂原生释放保护期，初值建议 iOS 500ms、Android 300ms，真机数据再调；保护期内其他广告触发器排队或放弃，不能并发 `show()`。页面隐藏时禁止启动新广告；广告覆盖导致的暂时隐藏不等于业务取消。

### 3.2 双广告位及错误处理

每个**小程序、每种广告类型、每个主广告位**登记同应用的一个备用位；主备 ID 可编入 v0.0.6 前端公开构建资源，用于快速创建实例，但服务端会话返回的允许列表、奖励次数、策略开关仍为权威。构建检查要拒绝空值、重复值、跨 appKey 混用和未登记的备用位。广告位 ID 可公开，Client Secret、播放授权和数据库凭据不可编进前端。未从 TikTok Portal 核准的备用位保持禁用，不用其他包的 ID 代替。

| 错误类 | 处理 | 是否切备用位 |
| --- | --- | --- |
| 已确认无填充/单广告位可用性问题 | 当前实例终态清理后，**同一业务序号最多切备用位一次**；新 `operationId`/`clientEventId`；记录主备角色 | 可以，前提是服务端会话允许且两位均在 Portal 核准。 |
| `50008` / `env check failed`、`not in foreground` | 若确实后台则等待下一次 `onShow` 后最多恢复一次；若已前台，停止本次自动重试并记录容器样本/上报平台 | 不切位；更换广告位不能修复同一原生环境检查。 |
| `11006` / 已有广告活跃 | 维持互斥及保护期，检查其他业务触发器；只有证实原生广告结束后才允许一次延迟重试 | 不切位。 |
| `11002` / 实例无效 | 丢弃实例，重新创建一次；重复出现熔断当前场景 | 默认不切位。 |
| `20001`、`20002` / 广告位或 Client Key 校验 | 停止自动轮换，核对 Portal 归属与当前 Client Key；原始消息与子码冲突时同时提交平台 | 不盲切。 |
| 客户端版本过低、SDK 能力不存在 | 提示升级/跳过自动广告，保留核心业务 | 不切位。 |
| `AD_SHOW_TIMEOUT`、`AD_CLOSE_TIMEOUT`、API 429/5xx | 标为 `CLIENT_TIMEOUT` 或 `API_HTTP`；先查原生终态/幂等结果，再决定业务重试 | 不因该错误自动切位。 |

主位失败切备用位不能与主位请求并行，也不能在主位可能仍展示时启动。错误分类依据**原始字段、来源和阶段**，中文说明只作诊断辅助；未知错误默认不切。相同 `sessionId + adIndex` 允许多个失败尝试，但只有一个确认的展示及完播计数。

### 3.3 连续激励、插屏和业务授权

剧集解锁：先取得奖励会话及主备允许列表；每一条激励广告使用新实例。只有 `onClose({isEnded:true})`，且该次 `show()` 的 `SHOWN` 事件已持久确认，才用同一 `clientEventId` 调 `/complete`。收到服务端 `shouldContinue=true` 后才准备下一条；关闭过早、SDK 失败或完成接口状态未定时停在当前序号，剧集仍锁定并允许用户稍后恢复。现有服务端验证的是**客户端广告事件证据**，不是 TikTok 独立签名完播证明，文案不得夸大。

入口 `SHOWN` 模式可保留顺序异步确认队列以缩短广告间网络等待，但新 release 的 `/shown` 必须核对同 `clientEventId + adIndex + 实际 placementId` 的 `SHOWN` 事件；最终放行前等待全部确认。入口 `COMPLETED` 继续只在完整观看后推进。自动入口广告不可用时按该 release 的 `onUnavailable` 决定放行，v0.0.6 默认 `ALLOW`；剧集奖励则绝不能因广告不可用放行付费集。免费集活动直达不触发入口广告补弹。

插屏只在自然切集且当前视频不在播放时评估；不与激励或入口广告重叠。初次启用建议每会话最多 2 次、最短间隔 180 秒、激励关闭后至少 60 秒冷却，均由后台配置而非官方强制数值。插屏 `onClose` 或失败后继续切集，不发奖励；定时插屏在 v0.0.6 保持关闭，特别要移除“正在播放时启动定时插屏”的 v0.0.5 分支行为。

## 4. 服务端接口契约与数据库迁移

### 4.1 向后兼容的接口变化

| 接口 | v0.0.6 增量字段/校验 | 旧包兼容 |
| --- | --- | --- |
| `POST /episodes/:episodeId/reward-session` | 新包传 `releaseId`；响应保留 `placementId`，新增 `placementIds: [primary, backup?]`、策略版本及 iOS/Android 加载模式。只有后台登记且主位匹配专辑 `accessConfig.rewardedPlacementId` 时给备用位。 | 未传 releaseId 仍用 `default`、单一位；保留已有奖励会话。 |
| `POST /app-entry-ad-sessions` | 响应附 `placementIds`；会话创建时冻结允许列表，避免管理员中途改位。 | 原 `placementId` 不变，空允许列表按 `[placementId]` 解释。 |
| `GET /episode-interstitial/config`、`GET /exit-retention/config` | 增加 `placementIds`、策略版本/加载模式；禁用时返回 `enabled=false`，不因前端内置 ID 自行展示。 | 原字段继续返回。 |
| `POST /ad-events` | `placementId` 必须为实际展示位，匹配会话允许列表；`SHOWN` 的 `clientEventId` 与业务序号保持稳定；失败诊断仍以 `/analytics/events` 为主。 | 旧会话按原单一位校验。 |
| `POST /app-entry-ad-sessions/:id/shown` | 新 release 请求携 `placementId`；先查对应 `AdEvent(SHOWN)` 再幂等推进计数，拒绝未授权/跳序位。 | 对旧 release 保留旧计数协议；不可在未升级客户端前强制必填。 |
| `POST /app-entry-ad-sessions/:id/complete`、`POST /episodes/:id/reward-session/:sid/complete` | 用同次持久 `SHOWN` 事件的实际广告位验证，而非固定等于会话主位；仍维持用户/剧集/序号/完播和幂等检查。 | 原单一位和旧事件 ID 行为继续有效。 |
| `POST /analytics/events`、`POST /playback-quality-events` | 接受下文新增的可选字段；继续批量、脱敏、限长、去重。 | 旧 payload 不变。 |

对入口 `SHOWN` 模式的增强需注意：当前 `/shown` 只按有序计数推进，新 release 改为依赖先写入的 `SHOWN` 事件；客户端可把两次 API 顺序放进异步确认队列，但不能在最终入口放行前忽略该队列的失败。网络重试复用同一事件 ID，不因 429/5xx 发起第二次原生 `show()`。

### 4.2 Prisma 增量模型

1. 新建 `AdPlacementPair`（每个小程序独立库）：`releaseId`、`adType`、`primaryPlacementId`、`backupPlacementId`、`enabled`、`iosLoadMode`、`androidLoadMode`、`iosExperimentPercent`、`version`、更新时间/操作者；唯一键建议 `(releaseId, adType, primaryPlacementId)`。专辑自定义主位通过相同主位查配对；未登记时只给原单一位。主备不可相同，均要符合广告位格式，禁止跨 Mini 配对。
2. `RewardedUnlockSession`、`AppEntryAdSession` 新增 `allowedPlacementIds String[] @default([])` 和可选 `placementPolicyVersion`。旧行数组为空时服务端按 `[placementId]` 解释；不回填、不重写已有会话。
3. `ClientAnalyticsEvent` 新增可空 `operationId`、`attemptNo`、`adPhase`、`errorOrigin`、`strategyVariant`、`placementRole`。`metadata.sdkCallback` 继续保留脱敏原对象，不为 SDK 没有给出的字段伪造值；按实际查询计划评估 `(miniAppKey, releaseId, platform, eventKey, receivedAt)` 及 `(miniAppKey, operationId)` 索引写入成本。
4. `PlaybackQualityEvent` 新增可空 `platform`、`tiktokClientVersion`、`stage`、`playerOperationId`、`preloadHit`。`clientVersion` 保留；旧数据不回填为猜测值。
5. 新迁移只加表/列/必要索引，不删除旧字段或数据。埋点表索引拆为两步：先在 `20261109090000_v006_ads_player_observability` 增加列；然后在事务外用 `psql -X -v ON_ERROR_STOP=1 -f deploy/v006-create-analytics-indexes-concurrently.psql` 并发建索引；最后由 `20261110090000_v006_analytics_indexes` 用 `IF NOT EXISTS` 登记索引。Prisma migration 会包事务，不能在 migration 文件里使用 `CREATE INDEX CONCURRENTLY`。索引脚本先清理上次失败留下的无效索引，并设置 5 秒锁等待上限。先在隔离数据库测试完整顺序，再对**每个候选 API 实际配置的独立数据库**逐库执行；预检只接受 `indisvalid` 且 `indisready` 的索引，全部通过后才能切流。

### 4.3 埋点和诊断约定

每次原生展示尝试生成 `operationId`；SDK `load`、`show`、`onError`、`onClose` 与 API 确认共享它，同时记录 `sessionId` 的脱敏关联值、`adIndex`、平台、广告类型/场景、主备角色、前台状态、实例创建到 `show()` 的间隔、是否显式 `load()`、回调来源及耗时。`clientEventId` 仍只承担业务幂等。`show.resolve` 代表 SDK 接受调用，不等于用户看完；`onClose.isEnded=true` 只用于激励完成判断。保留应用时间戳与服务端 `receivedAt`，不把二者混为网络耗时。

用一台 iOS 真机做端到端探针：调试台看到脱敏 `onError/onClose` 原对象 -> `/analytics/events` 返回 `202` 和 `accepted` -> 后台查询同 `operationId` -> 数据库 `metadata.sdkCallback` 非空。若仍为 0，按“发布包不一致 / 客户端未捕获 / 批次校验拒绝 / 上传失败 / 查询 JSON 路径错误”逐层定位。`tiktokClientVersion` 无官方可用字段时明确记 `unavailable` 和采集来源，不从用户代理字符串臆测具体版本。

首条展示尝试、成功、关闭、失败按 `operationId` 去重后才计算率；频繁重试样本可限流，但抽样率必须入库，不能拿抽样事件数当真实失败率。`AdEvent` 继续承载奖励和入口计数证据，不把高频 SDK 诊断灌入该业务表。诊断事件保留期和分区/归档由生产容量测试决定，避免大规模错误风暴压满数据库。

## 5. 播放器改造

1. 将播放失败分成 `PLAY_API_403/5XX`、获取播放器构造器、实例创建、`playNext`、`READY`、自动播放、缓冲、首个有效画面、媒体错误、播放授权过期等阶段；每次播放/切集分配 `playerOperationId`。不要把 API 403 当作播放器内核故障。
2. `DramaPlayerController.preparePreload` 对同一剧集只选择一条受控预加载路径：先去重，只保留当前和**已授权**下一集；Android 有可靠 MSE 能力时试 `prepare + setPreloadList`，不再同时对同批执行 `prefetchMediaInfo`；iOS 按官方能力和真机结果决定仅媒体信息预取或完全关闭视频预加载。预加载失败要埋点但不能阻塞当前播放。
3. 同专辑优先 `playNext`，失败只重建一次；切集时取消旧操作、解绑旧事件、清空过期预加载队列，避免旧事件更新新剧集 UI。已请求但未授权的下一集不得进入预加载列表，也不缓存长期播放 token。
4. `PlayerShell` 明确区分 `READY`、实际 `PLAYING` 和首帧近似事件；可用时结合媒体事件/首个画面，不能仅凭构造成功记首帧。自动播放失败显示一次用户可点击的播放按钮，保留已有受控重试上限；广告返回时等页面恢复前台后再尝试播放。
5. 确认播放器 root 的实际尺寸、视频层尺寸、`object-fit`，旋转/软键盘/切集后在容器稳定时调用 SDK 支持的 `resize()`；尺寸与 `vid` 可上报，播放凭证和带 token URL 不上报。对 iOS 低版本禁用视频预加载的判断以 TikTok 官方播放器文档与真机能力检查为准。
6. 后端继续按 `/episodes/:id/play` 逐集鉴权和签发播放信息；本期不新增“全专辑播放 token”接口。先用现有 `WatchPage` 的当前集/已授权下一集查询验证，只有证据表明 API 往返是主要瓶颈时再评估小批量接口。

### 共享 API 上线隔离门槛（2026-11-09 上线前记录；现状见第 10 节）

线上服务器仓库 HEAD 为 `140cbeb3c97ea23b29f8e417037c4539e0d33214`，但工作树有未提交修改，运行中容器由多个不同时间的镜像组成，不能把仓库 HEAD 当作实际 API 镜像版本。当前 Caddy 将四包的常规 API 请求交给 `api-b197e32-mounted`，将五包的 `/analytics/events` 和 `/admin/analytics/client-events` 交给 `api-five-analytics-candidate`。四个首发库及 ZenClip 均已应用 `20261106090000_client_analytics_event`，尚未应用后两项本地迁移。上线前应重新只读核对这些状态。

新 API 对旧 release 的奖励会话也会写入 `allowedPlacementIds` 等新列，因此**不能只迁移四个库却直接替换服务全部小程序的共享 API 容器**。有两种可执行路径：

1. 四包隔离灰度：先备份、在隔离 PostgreSQL 演练；为候选容器提供受控的数据库环境清单，仅包含确实需要注册的 Mini，注意 `buildApp` 总会注册 `main`。将候选环境中的主库和目标独立库先迁移至 `20261109090000_v006_ads_player_observability`，对埋点表运行 `psql -X -v ON_ERROR_STOP=1 -f deploy/v006-create-analytics-indexes-concurrently.psql`，再迁移 `20261110090000_v006_analytics_indexes`。运行下述预检并要求每库 `PASS`。首发只将 DramaFlicks 的完整业务路径交给候选容器作为 canary；验证后再逐包扩大。其他小程序及旧管理路径维持原上游。切换前后分别测试旧包请求的授权、广告计数、播放和埋点接口。
2. 共享 API 整体升级：先列出新镜像会注册的全部小程序数据库，逐库完成四项增量迁移；候选库包含目标表时，依次执行第 1 项中的并发索引阶段；之后运行下述预检，再替换共享容器。对每个旧包的核心接口做回归。任何一个库未迁移成功，都不切换共享路由。

`/ready` 目前只探测主库连通性，不能代替目标库迁移检查。**必须在候选 API 镜像内、使用与启动服务相同的环境变量**运行只读预检；脚本检查全部已配置小程序库（不只检查 `--expect` 列出的四包），并核对迁移记录、当前 schema、新列、旧 API 插入会话所需的非空默认值和索引。任一库失败即返回非零状态，禁止切换路由。在 `apps/api` 工作目录执行：

```bash
node dist/scripts/check-v006-schema.js --expect=dramaflicks,heartreel,sweetreel,luxereel
```

只灰度 DramaFlicks 时可将 `--expect` 改为 `dramaflicks`，但脚本仍检查候选环境里**所有**已配置的库，包括 `main`。不要用开发机的 `.env` 代替候选容器环境，也不要因 `/ready` 返回 200 而跳过此门槛。

上述两条路径都要先备份生产环境与数据库，并确认回退路由及旧镜像仍可用。这里记录的是 2026-11-09 上线前状态；其后完成的迁移和 canary 检查见第 10 节。TikTok Portal 广告位核验、iOS/Android 真机和 DramaFlicks 旧包完整业务冒烟仍未完成，不把“不会影响旧版本”作为已通过的验收结论。

回滚顺序：后台先关新 release 的自动入口/插屏、备用位和显式加载实验；停止新包灰度并切回上一 ZIP；API 保持新旧兼容版可运行，必要时回退 API 代码，但保留增量数据库结构，避免旧包与新包混用期间破坏会话。`/complete` 的幂等键和历史奖励记录不回滚、不批量删除。

## 8. 真机实验与量化验收

1. **iOS 因果实验**：在同一小程序、同一广告位、相近 TikTok 版本与流量时段随机分 `DIRECT_SHOW` / `EXPLICIT_LOAD`；每组至少积累 1,000 次**独立首次展示尝试**，或持续 24 小时后评估样本是否足够。记录系统版本、TikTok 版本/采集来源、前台状态、实例创建到 `show` 间隔、load 能力和回调原对象。若客户端版本仍不可采，按“未知版本”单独分析，不能强称已消除混杂。
2. **广告漏斗**：每包、OS、广告类型、release、位与策略组统计 `eligible -> show.call -> show.resolve -> onClose -> isEnded=true -> /complete`；分母用去重 `operationId`/会话。目标：`11006` 占展示尝试比例较同包基线下降至少 90%，且无重复奖励；iOS `50008` 的**首次尝试率**相对对照组下降至少 30% 才考虑放大直展策略。若未改善，保留保护措施并向 TikTok 升级原始样本，不宣称根因已解决。
3. **体验和负载**：iOS 首次成功展示率不得比对照组下降超过 2 个百分点；入口到首次成功展示的 p50/p95 和失败后可继续浏览时间分开看；`/analytics/events` 202 接收率、拒绝率、数据库 CPU/连接池和表增长不劣化。`sdkCallback` 覆盖率只针对 SDK 实际提供的 `onError/onClose` 样本计算，不要求所有事件都带回调。
4. **播放器**：分别在 iOS 支持/不支持 MSE 的机型和 Android 真机验证免费集、解锁后首播、连续 10 次切集、广告返回、后台恢复、弱网、token 过期、旋转和手动播放。以同包基线比较首帧 p50/p95、启动失败率、`playNext` 降级率和预加载命中率；错误率不能比基线高 0.5 个百分点以上，首帧 p95 不能变差超过 10%。
5. **兼容**：旧 v0.0.4.1/v0.0.5 包继续使用原单一广告位、原 API payload 和已保存的 release 策略；活动免费集直达不触发入口补弹。新包后台关闭策略时不因前端硬编码 ID 偷偷 `show()`。
