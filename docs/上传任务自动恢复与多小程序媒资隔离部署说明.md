# 上传任务自动恢复与多小程序媒资隔离

本次版本把本地视频上传改成“先落盘、再由 Worker 上传”。浏览器请求只负责把文件保存到持久化目录并创建 `PENDING` 任务；API 或 Worker 重启不会丢失文件。Worker 会按当前小程序、TikTok Client Key、BytePlus 账号、空间和地区计算上传作用域，并把作用域和任务 ID 写入 BytePlus 标签。

Worker 发现任务曾经开始过远端上传时，会先查询 VOD 的 `GetMediaInfos`/`GetMediaList`。只有同时满足当前 BytePlus 空间、当前作用域标签和当前任务标签的 VID 才会自动绑定。任务查询失败不会立即重新上传；BytePlus 返回成功但响应丢失时，也不会重复上传。不同小程序即使使用同一个 BytePlus 空间，也必须使用各自上传产生的 VID。

## 部署

在服务器执行。先确认 `.env.production` 中所有已启用小程序的 `*_DATABASE_URL`、TikTok 凭据和 BytePlus 凭据都已配置，不要把生产环境文件提交到 Git。

```bash
cd /opt/quickreels
export ENV_FILE=/opt/quickreels/.env.production
export COMPOSE_FILE=compose.production.self-hosted.yml

git fetch origin main
git merge --ff-only FETCH_HEAD

sudo docker compose --env-file "$ENV_FILE" -f "$COMPOSE_FILE" build api worker admin
```

备份主库和各小程序 schema 后，再对每个已启用 schema 执行迁移。`main` 对应 `DATABASE_URL`，其他 key 对应大写的 `<KEY>_DATABASE_URL`；以下循环会跳过没有配置 URL 的 key：

```bash
APP_KEYS=(main taletv cinereels talereels storyland dramacloud dailyreel dramaone dramaup dramavault talehub talebox storyworld storyhub dramaroom dramazone taleflick dramashort storyshort storyflicks dramaflicks crownrush sugarreel crimsonshorts sweetreel dramablaze heartreel dramahit crownreel luxereel elitedrama)

for key in "${APP_KEYS[@]}"; do
  if [ "$key" = main ]; then
    db_env=DATABASE_URL
  else
    db_env="${key^^}_DATABASE_URL"
  fi
  db_url="$(grep -E "^${db_env}=" "$ENV_FILE" | sed 's/^[^=]*=//')"
  [ -n "$db_url" ] || { echo "skip $key: $db_env not configured"; continue; }
  echo "migrate $key"
  sudo docker compose --env-file "$ENV_FILE" -f "$COMPOSE_FILE" run --rm --no-deps -T \
    -e APP_DB_ENV="$db_env" api sh -ec '
      db_url="$(printenv "$APP_DB_ENV")"
      test -n "$db_url" || exit 1
      export DATABASE_URL="$db_url"
      exec npx --no-install prisma migrate deploy
    '
done
```

如果 `SHARED_PLATFORM_DATABASE_URL` 配置为独立数据库，还要对它执行一次相同迁移；若它与主库相同则跳过：

```bash
shared_url="$(grep -E '^SHARED_PLATFORM_DATABASE_URL=' "$ENV_FILE" | sed 's/^[^=]*=//')"
main_url="$(grep -E '^DATABASE_URL=' "$ENV_FILE" | sed 's/^[^=]*=//')"
if [ -n "$shared_url" ] && [ "$shared_url" != "$main_url" ]; then
  sudo docker compose --env-file "$ENV_FILE" -f "$COMPOSE_FILE" run --rm --no-deps -T \
    -e APP_DB_ENV=SHARED_PLATFORM_DATABASE_URL api sh -ec '
      export DATABASE_URL="$(printenv "$APP_DB_ENV")"
      test -n "$DATABASE_URL" || exit 1
      exec npx --no-install prisma migrate deploy
    '
fi
```

确认 compose 配置和持久化卷后，重建 API、Worker、管理后台：

```bash
sudo docker compose --env-file "$ENV_FILE" -f "$COMPOSE_FILE" config --quiet
sudo docker compose --env-file "$ENV_FILE" -f "$COMPOSE_FILE" up -d --no-deps --force-recreate api worker admin
sudo docker compose --env-file "$ENV_FILE" -f "$COMPOSE_FILE" ps
curl -fsS https://api.evergreenprosper.com/ready
```

`api` 和 `worker` 必须都挂载 `video_uploads:/var/lib/quickreels/video-uploads`。不要只重启 API；没有这个卷时，服务器重启后无法恢复尚未完成的文件上传。

## 处理旧任务和第 21 集

1. 部署后等待 Worker 自动查询旧任务。旧任务若没有可恢复文件或 VID，会变成失败并解除分集占用；失败任务可重新选择视频排队。
2. 第 21 集如果绑定了其他组织的 VID，在当前小程序后台打开该剧的素材管理，点击“解除绑定并重传”，确认后重新选择该组织的视频文件。原 VID 不会被删除。
3. 如果接口提示仍有“平台分集、审核或待对账任务”，先处理对应任务；只有已完成平台映射的分集或正在审核的剧目才会阻止解除绑定。
4. 不要把另一个组织的 VID 手工绑定到当前小程序。系统会检查 BytePlus 标签、空间和共享媒资归属，并返回冲突提示。

## 验收

- 上传过程中重启 `api` 或 `worker`，文件仍在 `video_uploads` 卷中，任务最终变为 `SUCCEEDED` 或明确 `FAILED`。
- BytePlus 已产生 VID 但请求响应丢失时，任务自动绑定原 VID，日志中不应出现第二次上传。
- 另一小程序的 VID 不能在当前小程序登记；两个小程序上传同一集时应生成两个不同 VID。
- 管理后台不再要求输入 VID 对账；“自动核查”只会触发服务端 VOD 查询。
