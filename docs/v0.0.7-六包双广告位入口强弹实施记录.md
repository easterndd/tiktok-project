# v0.0.7 六包入口强弹同步记录

## 范围

ZenClip、StoryWorld、DailyReel、EliteDrama、SonicReel、OrbitPlay 的新 `*-v007-dual-*` 包复用 DramaFlicks 的入口强弹 V2 流程。`v0.0.7` 文件中每包两组激励位和两组插屏位是公开广告位 ID，已按原线上主位、第二个备用位的顺序写入 `apps/mini-web/scripts/v007-placements.mjs`。

旧 `*-attr1-*`、`v005` 等发布号继续走原分支。没有修改播放器逻辑、数据库结构、入口强弹展示次数或 IP 豁免优先级。

## 运行链路

1. 包启动时取得启动归因并创建入口会话。服务端先执行全局 IP 豁免，再执行归因判断和该发布号的入口策略；豁免或策略关闭时不展示广告。
2. 新包通过 `entryFlowVersion: 2` 请求入口会话。服务端核对小程序 App ID、发布号及原主广告位，返回该包的两位清单、展示次数、计数模式和不可用策略；不读取数据库广告位配对开关。
3. Android 并行准备两个激励广告位；第一条展示时补充下一条准备量，关闭后从已就绪位直接交接。iOS 只准备和展示主位。TikTok SDK 若不支持显式 `load()`，实例创建不保证素材已缓存，实际交接仍取决于 SDK 和网络。
4. 前端本地推进连弹次数，异步提交 `SHOWN`、`CLOSED_COMPLETED`、`CLOSED_INCOMPLETE` 观察记录。`SHOWN` 模式按展示计数，`COMPLETED` 模式按完播计数；中途不等待服务端逐条返回。后台仍按新发布号配置展示次数和开关。
5. 剧集解锁、剧集插屏、退出挽留保留各自策略。Android 可使用对应主备位，iOS 只用主位。入口 `enabled` 不控制这些独立广告流程。

## 发布与验收

- 六包 ZIP：`apps/<appKey>/dist/minis.config.zip`；对应发布号和 SHA-256 记录在同目录 `minis.release.json`。
- 新发布号需要复制对应小程序原入口策略，保留各包原有展示次数与计数模式，再按业务需要启用。旧发布号策略不变。
- API 必须先部署本次代码并通过六库 `check-v006-schema.js --expect=zenclip,storyworld,dailyreel,elitedrama,sonicreel,orbitplay`；六库已有所需结构时无需迁移。
- 验收 Android 时检查入口会话 `entryFlowVersion=2`、`ANDROID_DUAL_CLIENT`、两位清单及广告交接时间线；iOS 检查 `IOS_SINGLE_CLIENT` 和实际只展示主位。另检查归因及全局 IP 豁免判定。
- 本地测试和 API 灰度不能代替 TikTok Portal 上传后的 Android/iOS 真机验收。
