# QuicK ReeLS：内容创建、封面上传与连续激励广告开发手册

> 状态：后续开发基线
> 适用范围：`apps/admin-web`、`apps/api`、`apps/mini-web`、PostgreSQL/Prisma，以及 TikTok Minis / BytePlus 的服务端适配层。
> 本文把当前项目实现、已确认的产品要求和本地 TikTok Minis 官方文档摘要整合为可执行方案。它不是 TikTok API Reference 的替代品；所有 TikTok Short Drama、Media Asset、IAA 接口名、请求字段和审批要求必须在实施当天再以官方实时文档为准。

## 1. 本次要解决的问题

### 1.1 内容运营问题

当前运营后台只能为**已存在的 Episode**选择本地视频文件上传；无法上传本地封面，创建一部短剧及其目标剧集也缺少完整界面流程。

目标是把后台改造成一站式内容创建工作流：运营人员输入剧集信息、选择本地封面、按集录入或批量生成 Episode、选择每集视频，即可保存草稿并继续完成媒资上传和平台同步。

### 1.2 广告解锁问题

当前一个锁定 Episode 只要完成一次 Rewarded Ad 就永久解锁。产品需要改为：后台可配置“解锁该集需要获得多少次广告奖励”，例如 3 次。用户在每一条广告达到广告平台设定的奖励条件、随后关闭广告后，应自动连续展示下一条广告；累计达到配置次数后，才解锁并进入播放。

这不是“强制把一条广告创意播放到结尾”，也不是项目设置广告秒数。广告何时可领取奖励、何时可关闭、素材时长是多少，均由 TikTok IAA 和第三方广告方决定。

### 1.3 明确的 UX 要求

不要新增广告观看页面，不展示如下用户进度：

```text
正在解锁第 1/3 个广告
完成后将自动播放下一条广告
```

用户留在原剧集详情页。每次广告关闭并且 SDK 判定满足奖励条件后，应用无感地继续弹出新广告；最后一次成功后自动进入播放页。发生错误或用户提前退出时，剧集保持锁定，只展示通用、非次数性的可重试提示。

## 2. 当前工程现状与改造边界

| 层级 | 当前实现 | 改造结论 |
| --- | --- | --- |
| 管理后台 | 有本地视频文件选择和上传任务列表；无内容创建表单、无本地图片上传 | 新增“内容创建”与“封面上传”能力；上传视频时不再手工反复选择目标 Episode |
| API | `Album.coverUrl`、`Episode.coverUrl`、`tiktokCoverPicId` 已存在；创建 Album 时 `coverUrl` 必填且必须是 URL | 添加封面资产模型和图片上传接口；创建时传 `coverAssetId`，后端生成/保存展示 URL |
| 视频上传 | 本地视频上传到临时文件后调用 BytePlus；上传结果回写自动生成封面 | 自定义封面优先，BytePlus 自动封面仅作备用信息 |
| 广告解锁 | `EpisodeUnlock` 对 `(userId, episodeId)` 唯一；一次 `isEnded: true` 就创建永久解锁 | 新增“多次奖励会话”，只有次数达到配置值时才写入 `EpisodeUnlock` |
| Mini 前端 | 每次点击锁集只展示一条广告；`onClose({ isEnded })` 后请求解锁 | 改为无界面进度的顺序循环，每次展示都创建新广告实例 |
| 平台服务 | `TikTokShortDramaService` 当前是适配器边界，具体平台调用未落地 | 将本地封面上传和专辑/剧集同步放入该服务端边界；前端不得调用 TikTok/BytePlus 管理 API |

## 3. 官方与安全约束

### 3.1 TikTok Minis / IAA

1. 变现前必须完成企业认证、IAA 开通、相关协议签署和组织审批；实际 Rewarded Placement 必须是本 App、目标地区和环境下可用的 Active 状态。
2. Mini 端必须通过 `window.TTMinis` 调用客户端能力，调用激励广告前先检查 `canIUse('createRewardedVideoAd')`。
3. 每一次展示都新建一个 `RewardedVideoAd` 实例；不要缓存并重复展示旧实例。
4. 奖励资格以 SDK 回调为准：仅在广告关闭回调返回 `isEnded === true` 时，才向业务后端申领奖励次数。不能用浏览器计时器、广告素材总时长、页面停留时间或前端伪造字段决定奖励。
5. SDK 当前项目类型声明只暴露关闭回调的 `isEnded`；因此应用不能假设存在独立的“第 N 秒已奖励”回调。用户能够关闭广告时，广告平台会通过关闭回调表达该次是否达到奖励资格。
6. 后端仅记录来自已登录用户、Mini SDK 回调后的业务结果；除非官方提供可验证的服务器回调或签名，不能声称后端可独立证明广告实际播放情况。

### 3.2 内容与封面

1. Mini 前端请求的 API、封面 CDN 和其他运行时域名必须使用 HTTPS，并登记到 Developer Portal 的可信域名 allowlist；不可使用路径或通配符。
2. 后台和 API 是独立运营系统，不能被打进 TikTok Mini ZIP；所有 BytePlus AK/SK、TikTok Client Secret、Media API 上传凭据均只能在服务端保存。
3. 数据库保存元数据、资源 ID、展示 URL、哈希和状态，不保存视频文件二进制。封面二进制可在对象存储中持久化；不要把生产封面仅放到容器临时目录。
4. TikTok Short Drama 的图片、专辑、剧集、审核、online version 和 listing 使用实时官方 API Reference 实现。本文中的服务接口是项目内部 DTO，不是官方方法签名承诺。

### 3.3 推荐限制

- `rewardedAdCount` 建议范围 `1..10`，默认 `1`。超出范围可能造成糟糕体验或配置事故。
- 同一用户、同一 Episode 同一时刻最多存在一个活动解锁会话。
- 给活动会话设置过期时间（建议 30 分钟）；会话过期后重新开始，但已经永久解锁的 Episode 永远可播放。
- 对创建会话、完成奖励事件、广告事件接口做用户级限流和审计。

## 4. 目标用户流程

### 4.1 运营人员：创建并上传一部短剧

```text
打开“内容创建”
-> 填写剧名、简介、语言、地区、广告策略
-> 选择本地专辑封面，后台上传并显示预览
-> 输入总集数或添加 Episode 行
-> 系统创建 Album 草稿与全部 Episode 草稿
-> 在每一集选择本地视频；可批量选择并按文件名匹配
-> 服务端上传到 BytePlus 并写入 Vid、时长、自动封面等信息
-> 自定义封面优先保留；自动封面仅作为备用
-> 运营补充/确认元数据
-> 服务端同步图片、Album、Episode 到 TikTok Short Drama
-> 提交审核，审核通过后设置 online version / listing
```

### 4.2 用户：需要看三次广告解锁一集

```text
用户点击锁定 Episode
-> 若未登录，执行 TikTok Login 并返回原操作
-> API 创建或恢复活动 RewardedUnlockSession（requiredCount=3）
-> Mini 创建新的 RewardedVideoAd 并展示

广告平台决定奖励门槛与可关闭时点
-> 用户关闭广告
-> SDK onClose({ isEnded: true })
-> API 原子累计一次奖励，completedCount=1
-> 未达 3 次：Mini 立即创建新的广告实例并展示下一条

第三条广告满足奖励条件并关闭
-> API 原子累计，completedCount=3
-> API 创建 EpisodeUnlock 并将会话设为 UNLOCKED
-> Mini 刷新目录访问状态并跳转 /watch/:albumId/:episodeId
```

异常分支：

| 情况 | 行为 |
| --- | --- |
| 用户在奖励条件前关闭广告，`isEnded=false` | 不计数，不解锁，停止连续展示；用户下次点击可恢复会话 |
| 广告加载或播放报错 | 不计数，停止连续展示，给出通用“暂时无法解锁，请稍后重试”提示 |
| 奖励回调成功但 API 网络超时 | 使用同一个 `clientEventId` 重试完成接口，避免丢失或重复计数 |
| 用户关闭/刷新 Mini | 会话仍保留至过期；下次点击锁集恢复会话并继续剩余次数，不显示进度 |
| 后台把规则从 3 改为 5 | 已创建会话仍按创建时冻结的 3 次完成；新会话按 5 次执行 |
| Episode 已被其他设备解锁 | 创建/完成会话接口返回 `PLAYABLE`，前端直接播放，不再弹广告 |

## 5. 内容创建与本地封面方案

## 5.1 后台信息架构

增加一个一级标签页：`内容创建`。保留现有“上传任务”，使它专门用于上传队列、失败重试和结果排查。

“内容创建”采用单页分段表单，草稿可保存：

| 区域 | 字段/动作 |
| --- | --- |
| 基础资料 | 剧名、简介、语言、投放地区、题材、初始状态 |
| 专辑封面 | 本地图片选择、预览、替换、删除、上传状态 |
| 访问与广告 | 免费集数、启用广告、Rewarded Placement ID、每集广告奖励次数 |
| Episode | 总集数快速生成；逐集编辑集号、标题、排序、是否免费、可选 Episode 独立封面 |
| 视频 | 每集选择文件；支持多选和文件名匹配；显示上传中/成功/失败；单集重试 |
| 发布 | 保存草稿、同步平台、提交审核、上架、下架；根据状态显示可用按钮 |

不要让运营人员在“上传视频”前必须先去另一个页面手动创建 Album 和 Episode。首次“保存并创建”应当用一个后端事务创建整个草稿结构，并把返回的 Episode ID 绑定到前端行。

### 5.2 封面资产模型

新增 Prisma 模型，命名可以为 `CoverAsset`（如未来会扩展海报、首页横幅、字幕附件，可升级为通用 `MediaAsset`）：

```prisma
enum CoverAssetStatus {
  UPLOADING
  READY
  FAILED
  DELETED
}

model CoverAsset {
  id              String           @id @default(cuid())
  storageKey      String           @unique
  publicUrl       String
  providerImageId String?          @unique
  mimeType        String
  fileSize        Int
  width           Int?
  height          Int?
  sha256          String           @unique
  status          CoverAssetStatus @default(UPLOADING)
  createdAt       DateTime         @default(now())
  updatedAt       DateTime         @updatedAt

  albumCovers     Album[]          @relation("AlbumCoverAsset")
  episodeCovers   Episode[]        @relation("EpisodeCoverAsset")
}
```

在 `Album` 和 `Episode` 上增加可空外键：

```prisma
coverAssetId String?
coverAsset   CoverAsset? @relation("AlbumCoverAsset", fields: [coverAssetId], references: [id])
```

`Episode` 使用独立关系名。保留已有 `coverUrl`、`byteplusCoverUrl`、`tiktokCoverPicId`：

- `coverUrl`：对 Mini 展示的最终 URL；应始终对应自定义封面优先的结果。
- `byteplusCoverUrl`：视频上传后供应商自动生成的封面，仅作回退或运营参考。
- `tiktokCoverPicId`：同步到 TikTok Media Asset 后得到的图片资源标识。
- `coverAssetId`：项目内封面资产实体的稳定关联。

### 5.3 存储抽象

不要在 `admin/routes.ts` 内直接耦合本地磁盘或某一个云厂商。定义内部接口：

```ts
export interface ObjectStorageService {
  putObject(input: {
    key: string;
    filePath: string;
    contentType: string;
  }): Promise<{ storageKey: string; publicUrl: string }>;
  deleteObject(input: { storageKey: string }): Promise<void>;
}
```

环境建议：

- 开发：受控本地目录或开发对象存储；API 通过受保护/静态资源路由提供 URL。
- 生产：S3 兼容对象存储或团队已选 CDN/对象存储；配置专用 Bucket、生命周期、私有上传权限和公共/签名读取策略。
- 临时文件：仅用于接收 multipart 内容；上传/同步完毕后立即删除。不能将其作为长期资源地址。

### 5.4 本地封面上传接口

新增：

```text
POST /api/v1/admin/cover-assets
Content-Type: multipart/form-data
字段：file
```

处理顺序：

1. 管理员鉴权。
2. 校验只接收一个文件；推荐 PNG、JPEG、WebP。实际可接收格式以 TikTok 图片 API 实时限制为准。
3. 校验文件扩展名和解码后 MIME 类型一致；不要仅相信浏览器提交的 `Content-Type`。
4. 限制文件大小、像素总数、宽高比；运营推荐专辑封面 3:4，像素限制使用可配置参数。
5. 流式写入临时文件，同时计算 SHA-256。发现同哈希已存在且状态为 READY 时直接复用，避免重复传输。
6. 上传对象存储，建立 `CoverAsset`，状态置为 READY。
7. 需要在创建时即平台同步时，服务端调用当前官方图片/Media Asset API，保存 `providerImageId`/`tiktokCoverPicId`；平台暂不可用时保持项目内 READY，并在“同步平台”任务中重试。
8. 返回 `assetId`、`publicUrl`、图片元数据与状态；不返回存储凭据。

响应示例：

```json
{
  "id": "cover_cx1",
  "publicUrl": "https://cdn.example.com/covers/cover_cx1.jpg",
  "providerImageId": null,
  "status": "READY",
  "width": 900,
  "height": 1200
}
```

封面在 Album/Episode 编辑接口中传递 `coverAssetId`，服务端校验资产为 READY 并把 `coverUrl` 投影为资产的 `publicUrl`。前端不要自行将本地 `blob:` URL 写入数据库。

### 5.5 视频上传与封面优先级

修改本地视频上传完成逻辑。当前上传成功会写入 `byteplusCoverUrl`；改造后使用：

```text
若 Episode.coverAssetId 存在且封面资产 READY：
  byteplusCoverUrl = provider 自动封面
  coverUrl = CoverAsset.publicUrl（保持不变）
否则：
  byteplusCoverUrl = provider 自动封面
  coverUrl = provider 自动封面
```

Album 也使用同样的优先级。这样用户主动上传的本地封面永远不会被视频自动截帧覆盖。

### 5.6 创建内容接口

新增业务聚合接口：

```text
POST /api/v1/admin/dramas
```

请求示例：

```json
{
  "title": "Example Drama",
  "description": "Drama introduction",
  "coverAssetId": "cover_cx1",
  "language": "en",
  "regions": ["US"],
  "accessConfig": {
    "freeEpisodeCount": 3,
    "rewardedAdEnabled": true,
    "rewardedPlacementId": "rewarded_episode_unlock",
    "rewardedAdCount": 3
  },
  "episodes": [
    {
      "episodeNo": 1,
      "title": "Episode 1",
      "sortOrder": 1,
      "isFree": true,
      "coverAssetId": null
    }
  ]
}
```

后端校验并在单个 Prisma transaction 中：

1. 检查专辑和每集封面资产的所有权/状态。
2. 创建 `Album(status=DRAFT)`。
3. 批量创建全部 `Episode(status=DRAFT)`，保证 `(albumId, episodeNo)` 唯一。
4. 写 `AuditLog(CREATE, Drama)`，保存不可敏感的摘要。
5. 返回 Album 和按输入顺序排列的 Episode ID，供前端立即绑定视频上传。

保留既有 `POST /admin/albums`、`POST /admin/episodes` 作为低层维护接口，但新后台常规流程应只调用聚合接口。

### 5.7 批量文件匹配

前端可支持用户选择多个文件，识别文件名的优先规则：

```text
第01集.mp4 / 第1集.mp4
Episode 01.mp4 / Episode 1.mp4
E01.mp4
S01E01.mp4
```

匹配规则仅用于**预填和提示**，不得自动覆盖运营人员已手动指定的 Episode。无法匹配、重复匹配或缺失文件时高亮行，并让运营人员手动选择。后台永远使用 Episode 的本地 ID，而不是根据文件名推断保存目标。

## 6. 连续激励广告解锁方案

## 6.1 配置模型

扩展 `apps/api/src/lib/content-access.ts` 中的 `accessConfigSchema`：

```ts
export const accessConfigSchema = z.object({
  freeEpisodeCount: z.number().int().min(0).max(10_000).default(0),
  rewardedAdEnabled: z.boolean().default(true),
  rewardedPlacementId: z.string().trim().min(1).max(128).default('rewarded_episode_unlock'),
  rewardedAdCount: z.number().int().min(1).max(10).default(1)
}).default({
  freeEpisodeCount: 0,
  rewardedAdEnabled: true,
  rewardedPlacementId: 'rewarded_episode_unlock',
  rewardedAdCount: 1
});
```

兼容性要求：已有 Album 的 `accessConfig` 没有 `rewardedAdCount` 时，解析后必须自动按 `1` 处理，确保已发布内容行为不变。

后台配置展示为“解锁需获得广告奖励次数”；不要标记成“广告秒数”或“播放时长”。

## 6.2 解锁会话模型

`EpisodeUnlock` 仍是最终的永久授权记录，不承担中间计数。新增 `RewardedUnlockSession`：

```prisma
enum RewardedUnlockSessionStatus {
  ACTIVE
  UNLOCKED
  ABANDONED
  EXPIRED
}

model RewardedUnlockSession {
  id             String                      @id @default(cuid())
  userId         String
  episodeId      String
  placementId    String
  requiredCount  Int
  completedCount Int                         @default(0)
  status         RewardedUnlockSessionStatus @default(ACTIVE)
  expiresAt      DateTime
  createdAt      DateTime                    @default(now())
  updatedAt      DateTime                    @updatedAt

  user           User                        @relation(fields: [userId], references: [id], onDelete: Cascade)
  episode        Episode                     @relation(fields: [episodeId], references: [id], onDelete: Cascade)
  rewards        RewardedUnlockReward[]

  @@index([userId, episodeId, status, expiresAt])
}

model RewardedUnlockReward {
  id              String                @id @default(cuid())
  sessionId       String
  clientEventId   String
  adIndex         Int
  adEventId       String?
  createdAt       DateTime              @default(now())

  session         RewardedUnlockSession @relation(fields: [sessionId], references: [id], onDelete: Cascade)

  @@unique([sessionId, clientEventId])
  @@unique([sessionId, adIndex])
}
```

在 `User` 与 `Episode` 加上相应关系。`AdEvent` 可增加 `rewardSessionId` 和 `adIndex`，用于运营分析；该关系不是统计正确性的唯一来源，奖励去重必须以 `RewardedUnlockReward` 的唯一索引实现。

### 6.3 为什么要有会话

只在 `AdEvent` 上 count 有以下问题：用户刷新、并发点击、网络重试、后台规则修改、不同设备同时操作时都难以保证正确。会话将一次解锁的规则快照、已完成数量和生命周期放入数据库，由事务原子更新。

`requiredCount` 在创建时从 Album 配置读取并冻结。设置从 3 改到 5 不影响已开始会话；新会话采用 5。此规则避免用户正在看第 3 条广告时被运营配置变更突然加码。

## 6.4 API 设计

### 创建或恢复会话

```text
POST /api/v1/episodes/:episodeId/reward-session
Authorization: Bearer <user token>
```

处理规则：

1. 校验用户、Episode/Album 为 ONLINE、地区可见。
2. 如果 Episode 免费或已经存在 `EpisodeUnlock`，返回 `access=PLAYABLE`，不创建会话。
3. 读取 `accessConfig`；广告未启用或 Placement 不匹配时返回可识别的冲突错误。
4. 查找该用户该集尚未过期的 `ACTIVE` 会话，有则恢复；没有则创建一个，并把 placement 和 `requiredCount` 快照写入。
5. 返回实现循环所需的最少技术数据；Mini 不必渲染 completed/required 字段。

响应示例：

```json
{
  "access": "REWARDED_AD_REQUIRED",
  "sessionId": "rus_xxx",
  "placementId": "rewarded_episode_unlock"
}
```

### 记录一次已获得的广告奖励

```text
POST /api/v1/episodes/:episodeId/reward-session/:sessionId/complete
Authorization: Bearer <user token>
```

请求：

```json
{
  "clientEventId": "a-uuid-created-for-this-ad-instance",
  "isEnded": true
}
```

服务端**不接受客户端提交 completedCount 或 adIndex**。计数与下一个序号由服务端事务计算。

处理规则（必须单一事务）：

```text
锁定/读取会话和最终解锁记录
-> 验证 session 属于当前 user、episode 匹配、ACTIVE 且未过期
-> isEnded 必须 true
-> 若 clientEventId 已出现：返回此前的幂等结果，不再加一
-> 创建 RewardedUnlockReward（adIndex = completedCount + 1）
-> 创建/更新 AdEvent(CLOSED_COMPLETED)
-> completedCount 加一
-> 若 completedCount < requiredCount：返回 shouldContinue=true、access=REWARDED_AD_REQUIRED
-> 否则创建或 upsert EpisodeUnlock(REWARDED_AD)
-> session.status = UNLOCKED
-> 返回 shouldContinue=false、access=PLAYABLE
```

响应示例：

```json
{
  "access": "REWARDED_AD_REQUIRED",
  "shouldContinue": true
}
```

最终一条广告成功时：

```json
{
  "access": "PLAYABLE",
  "shouldContinue": false
}
```

`completedCount` 与 `requiredCount` 可以出现在服务端日志、运营分析或调试响应中，但常规 Mini UI 不展示它们。

### 记录未完成/失败事件（可选但推荐）

保留现有 `/ad-events`，记录：

- `REQUESTED`：准备展示广告。
- `SHOWN`：广告开始展示。
- `CLOSED_INCOMPLETE`：`isEnded=false`。
- `FAILED`：SDK `onError` 或 `show()` 拒绝。

这些事件不能改变 `completedCount`。为保证 session 事件关联，添加可选 `rewardSessionId`。若事件上报失败，不应阻塞 SDK 广告的关闭或造成错误解锁；最终奖励累计接口才是授权关键路径。

## 6.5 Mini 前端实现

将当前单次 `unlockEpisodeByRewardedAd(episodeId)` 改为“创建/恢复会话 + 顺序展示”的实现，但函数仍可在成功时只返回 `Promise<void>`，使 `AlbumPage` 调用方基本不变。

关键点：

1. 每轮 `window.TTMinis.createRewardedVideoAd` 都创建新实例。
2. 每轮生成一个新的 UUID，作为该广告展示的 `clientEventId`。网络重试必须复用同一 UUID。
3. `onClose` 为 `isEnded=false` 时停止循环并 reject；不尝试下一条广告。
4. `onClose` 为 `isEnded=true` 时，调用完成接口；服务端 `shouldContinue=true` 才继续下一轮。
5. 每轮等待结束后再发起下一轮，不能同时并行调用两个 `show()`。
6. 不添加次数文案、倒计时、独立页面或“继续”按钮；广告层连续出现由程序自动驱动。

推荐伪代码：

```ts
export async function unlockEpisodeByRewardedAds(episodeId: string): Promise<void> {
  if (!window.TTMinis?.canIUse('createRewardedVideoAd')) {
    throw new Error('Rewarded ads are unavailable on this TikTok version.');
  }

  const session = await apiClient.post<{
    access: 'PLAYABLE' | 'REWARDED_AD_REQUIRED';
    sessionId?: string;
    placementId?: string;
  }>(`/episodes/${episodeId}/reward-session`, {});

  if (session.access === 'PLAYABLE') return;
  if (!session.sessionId || !session.placementId) throw new Error('Rewarded ad session is unavailable.');

  let shouldContinue = true;
  while (shouldContinue) {
    const clientEventId = crypto.randomUUID();
    const completed = await showOneRewardedAd(session.placementId, clientEventId);
    if (!completed) throw new Error('AD_REWARD_NOT_EARNED');

    const result = await apiClient.post<{
      access: 'PLAYABLE' | 'REWARDED_AD_REQUIRED';
      shouldContinue: boolean;
    }>(`/episodes/${episodeId}/reward-session/${session.sessionId}/complete`, {
      clientEventId,
      isEnded: true
    });

    shouldContinue = result.shouldContinue;
  }
}
```

`showOneRewardedAd` 负责注册与移除 `onClose`、`onError`，以及调用 `ad.show()`；无论成功、提前退出还是报错都必须 cleanup，防止前一次实例监听器残留到下一条广告。

### 6.6 UI 行为

在 `AlbumPage`：

- 点击锁集后可以沿用已有加载态，避免用户重复点击。
- 不渲染次数、进度、广告时长、已看条数。
- 全部成功后 invalidate `['episodes', albumId, locale]`，然后导航到 `/watch/${albumId}/${episodeId}`。
- 提前关闭可用简短文案：“完成广告奖励后即可解锁本集。”
- 不可用或加载失败可用简短文案：“暂时无法加载广告，请稍后重试。”
- 不把服务端错误文本、广告网络详情或内部 session ID 直接呈现给用户。

### 6.7 并发和幂等

这是 P0 正确性要求，不可省略：

- `clientEventId` 对每次广告实例唯一；完成接口重复调用只能得到同一结果。
- PostgreSQL 事务应使用行锁或 Prisma 的可串行事务策略，避免同一会话的两个完成请求同时读到相同 `completedCount`。
- `@@unique([sessionId, clientEventId])` 防重试，`@@unique([sessionId, adIndex])` 防并发重复加数。
- 任何完成接口执行前先检查 `EpisodeUnlock`；其他设备已经解锁时返回 PLAYABLE，不再新增奖励记录。
- 达到 requiredCount 后，`EpisodeUnlock.upsert` 和 session 更新必须同一事务完成。

## 7. TikTok 与 BytePlus 平台同步

平台调用应只在 `apps/api` 服务端运行，并继续通过 `TikTokShortDramaService` 等适配器隔离。建议将接口扩展为以下业务概念：

```ts
interface TikTokShortDramaService {
  uploadCover(input: {
    sourceUrl: string;
    title?: string;
  }): Promise<{ providerImageId: string }>;

  createAlbum(input: Record<string, unknown>): Promise<{
    providerAlbumId: string;
    version?: number;
  }>;

  updateAlbum(input: {
    providerAlbumId: string;
    version?: number;
    album: Record<string, unknown>;
    episodes: Array<Record<string, unknown>>;
  }): Promise<{
    version?: number;
    episodeIdMap?: Record<string, string>;
  }>;

  submitReview(input: { providerAlbumId: string; version?: number }): Promise<void>;
  setOnlineVersion(input: { providerAlbumId: string; version?: number }): Promise<void>;
  setListing(input: { providerAlbumId: string; listed: boolean }): Promise<void>;
}
```

建议同步顺序：

```text
封面资产 READY
-> 上传/确认 TikTok 图片资源，保存 providerImageId
-> 本地视频上传完成，保存 BytePlus Vid、时长、自动封面
-> 创建或更新 TikTok Album 和 Episode 元数据，使用自定义封面图片 ID 优先
-> 保存 tiktokAlbumId、version、tiktokEpisodeId
-> 提交审核
-> 审核通过后设为 online version
-> 设置 listing
-> 本地 Album/Episode 转为 ONLINE
```

必须在同步前检查：封面资源可访问、每个要发布 Episode 有 BytePlus Vid、平台 ID 映射正确、内容状态有效。不要因本地视频上传成功就将公开 Episode 标记为 ONLINE。

## 9. 测试与验收

### 9.1 后端单元/集成测试

封面：

- JPEG/PNG/WebP 可上传；非法 MIME、空文件、超限文件、损坏图片被拒绝。
- 同哈希图片重复上传返回可复用资产或不创建重复对象。
- 对象存储失败后临时文件被删除，资产状态为 FAILED 或事务回滚。
- 有自定义封面时视频上传不会修改 `coverUrl`；无自定义封面时回退为 BytePlus 封面。
- 创建 Drama 失败时 Album/Episode 不留下部分数据。

广告：

- 没有 `rewardedAdCount` 的旧配置按 1 次工作。
- 配置 3 次时，前两次 complete 返回 `REWARDED_AD_REQUIRED`，第三次才返回 `PLAYABLE`。
- 同一 `clientEventId` 重试不增加 `completedCount`。
- 并发完成请求最多只增加一次；`completedCount` 不超过 `requiredCount`。
- `isEnded=false` 不能调用完成累计逻辑。
- 会话过期、用户/episode 不匹配、Placement 不匹配均拒绝。
- 最后一次完成后同时存在 `EpisodeUnlock` 与 `UNLOCKED` 会话。
- 已永久解锁时创建会话直接返回 PLAYABLE。

### 9.2 管理后台验收

- 可从本地选择并预览封面，无需手填公网 URL。
- 可以一次保存一部短剧和多集 Episode 草稿。
- 选择多视频后能正确预匹配，无法匹配时可以手动调整。
- 单集上传失败可重试，不影响其他集。
- 自定义封面在重新上传视频后仍然存在。
- 广告次数可配置，默认值为 1，保存后新解锁会话立刻采用新规则。

### 9.3 TikTok 真机验收

- 使用可用 Rewarded Placement 和真实测试账号。
- 调用前成功通过 `canIUse('createRewardedVideoAd')`。
- 对配置为 3 的 Episode，用户每一次达到广告平台奖励条件并关闭广告后，自动出现下一条广告。
- 用户在奖励条件前关闭广告时，次数不增加、Episode 不解锁、不会继续强弹下一条。
- 第三次有效奖励后才进入播放器。
- 页面上不显示广告次数、广告时长、广告观看进度或独立广告页。
- 广告不可用、网络中断、接口超时时，不能错误解锁；恢复后可继续。

## 10. 不应采用的方案

1. **前端定时 N 秒后自行加次数**：广告奖励时长不是应用控制项，且可以被篡改。
2. **用广告视频总时长判断是否奖励**：广告素材可能允许在特定门槛后关闭，素材总时长不等于奖励门槛。
3. **只在前端保存已看次数**：刷新、换设备或篡改本地状态即可绕过。
4. **每次广告完成就立即写 `EpisodeUnlock`**：会破坏多次广告规则。
5. **为每条广告重用同一个广告实例**：违背当前项目文档中的推荐方式，且容易产生回调和加载问题。
6. **把封面塞进数据库 BLOB 或容器临时目录**：成本、备份、扩展与重启恢复都不可控。
7. **将 TikTok/BytePlus 密钥发给管理后台浏览器**：违反项目信任边界。
8. **把多次广告次数直接展示给用户**：与本次产品 UX 要求冲突。

## 11. 关键决策记录

| 决策 | 结论 | 原因 |
| --- | --- | --- |
| 广告奖励依据 | 仅认 `onClose` 的 `isEnded === true` | 奖励门槛由广告平台决定，项目不设置秒数 |
| 多次计数位置 | 后端会话状态机 | 保证并发、刷新、重试、跨设备的正确性 |
| 最终解锁时点 | 达到会话 `requiredCount` 后 | `EpisodeUnlock` 保持永久访问授权的单一职责 |
| 是否展示次数 | 不展示 | 明确产品要求 |
| 广告连续方式 | 当前广告成功关闭后自动创建并展示下一实例 | 不要求用户额外点击，且避免同时展示多个实例 |
| 封面存储 | 对象存储 + 元数据表 | 支持本地上传、持久化、CDN 和平台同步 |
| 自动封面优先级 | 自定义封面优先 | 避免视频上传覆盖运营选择 |
| 内容创建方式 | `POST /admin/dramas` 聚合事务 | 降低“先创建目标剧集再上传”的运营成本 |
