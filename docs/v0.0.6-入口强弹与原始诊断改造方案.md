# v0.0.6 入口强弹与原始诊断改造方案

状态：本地代码已实施并通过单测与构建，数据库迁移、部署和真机验收待完成。依据 2026-11-10 本地源码、`广告优化.zip` 的 `index.html`/`_t21.js` 和用户真机视频。本文只规定入口强弹的新链路；剧集解锁、退出挽留、剧集插屏仍按各自配置与权益规则运行。

## 1. 目标与边界

1. 入口时从服务器取得一次权威配置：是否强弹、广告类型、主/备广告位允许清单、目标次数、计数方式、不可用处理和策略版本。**本次入口的选位、预加载、`show()`、关闭、计数、是否继续和页面放行均由前端决定；两条广告之间没有服务端等待。**服务器只异步接收运行记录，不参与下一条的决策。
2. Android 使用同应用的两个广告位：同一 ID 的 `load()` 串行，不同 ID 可并行；首条就绪后扩池，在播放期间准备后续实例，关闭后优先取已就绪实例立即展示。iOS 保持主位单广告位和现有兼容路径。
3. 保存客户端**可观察到的** SDK 调用与原始回调快照、项目 HTTP 请求/响应、服务端请求与错误日志，并能用一次入口会话串联排障。
4. `TTMinis.createRewardedVideoAd(...).show()` 是设备内 SDK 调用。客户端无法读取 TikTok 宿主内部发出的广告 HTTP 包、请求头、响应体或平台私有调度状态；“完整原始”限定为 JavaScript 实际收到的参数、回调/拒绝对象及本项目 HTTP 交换。旧记录无法补回这些数据。

## 2. 已确认的空窗来源

当前链路是 `POST /app-entry-ad-sessions` 获取会话，然后每条 `show()`，上报 `/ad-events`，在 `SHOWN` 模式调用 `/shown`，在 `COMPLETED` 模式关闭后调用 `/complete`，最后放行页面。`SHOWN` 的上报有序异步执行，**中间条目不会等待 HTTP 响应**；如果实测仍有空窗，应先检查本地交接和 ready 池，不应直接归咎于该接口。`COMPLETED` 则确实在每条关闭后等待 `/complete` 的响应，遇到 `AD_NOT_ACKNOWLEDGED` 还可能等待 `/ad-events` 补报并重试；这是额外的网络空窗。

**双广告位与交接等待是两个独立问题。** A、B 两位并行准备素材，可以让下一支在当前广告播放期间 ready；用户提供的参考实现真机已验证可做到视觉上无缝衔接。当前项目虽然也配置 A、B 双位，但 `claimNativeAd()` 的冷却锁按**整个原生广告活动**生效，不按广告位 ID 区分。因而“有两个 ID”本身不能证明当前入口代码已采用参考包的关闭后立即交接时序。以下是源码中可能造成空窗的路径，具体哪条在某次实测中触发，仍须按 release/OS 的时序记录判断。

| 位置 | 当前行为 | 对连播的影响 |
| --- | --- | --- |
| `ad-activity.ts` | Android 释放后固定冷却 300 ms；`claimNativeAd()` 在冷却期间返回 `AD_BUSY`，无论下一条选 A 还是 B | **若**下一条在冷却期内尝试，`entry-ad-flow.ts` 再等待至少 1000 ms 重试；这是可复现的代码路径，不是已证实的每次真机空窗原因。 |
| `entry-ad-flow.ts` | `COMPLETED` 每次关闭后 `await actions.complete()` | 往返延迟、服务端事务和补报竞争都计入两条广告间隔。`SHOWN` 避开此项，但仍受本地锁和池状态影响。 |
| `app-entry-ad.ts` | `onClose` 同步记录、解绑、销毁、预热后才 `resolve`；备用位回退固定等待 650 ms | 主线程工作与失败回退继续扩大间隔。关闭回调里的预热还与下一次展示争用。 |
| `ad-instance-cache.ts` | 全局池上限 4，每个广告位只预热 1 个；取池中第一个而非已就绪优先 | 播放很快结束时下一条可能尚在加载；展示路径最多再等 8 秒。 |

之前提供的当前包视频可见广告与首页交替；用户对双广告位参考实现的真机测试可做到视觉上无缝。两份证据可以同时成立，差异应由**具体构建 release、计数模式、双位是否都 ready、交接锁、实际广告位轮换**来解释。视频抽帧不足以给出精确毫秒数。新包须同时记录 `onClose -> next show.call`、`onClose -> next show.resolve` 和页面可见帧，分清 JS 调度和 TikTok 原生转场。

## 3. 入口协议重构

### 3.1 一次配置请求

沿用 `POST /app-entry-ad-sessions` 作为**唯一阻塞入口配置请求**，不在每条广告后向服务器询问“是否继续”。该请求一次完成当前已有的 release 策略、归因、用户/IP 豁免判断，返回 `required`、`sessionId`、`mode`、`requiredCount`、`countMode`、`placementIds`、`adLoadMode`、`onUnavailable`、`policyVersion`、`expiresAt` 和 `entryFlowVersion: 2`。没有返回 `required:true` 就不启动入口广告；前端硬编码广告位不能绕过 `enabled`。主备 ID 仍须与前端 manifest、App ID 及服务端允许清单匹配。旧 release 继续得到 v1 行为。

| 时点 | 现有 v1 | 新入口 v2 |
| --- | --- | --- |
| 启动 | `POST /app-entry-ad-sessions`，等待配置/会话 | 保留同一次请求，取得目标次数和允许广告位 |
| 每次 `show()` 后 | `SHOWN` 模式：排队 `POST /ad-events` 再 `/shown`；`COMPLETED` 模式：后台报 `SHOWN` | 前端立即更新本地状态；诊断入本地发送箱，不等 HTTP |
| 每次 `onClose` 后 | `COMPLETED` 等 `/complete` 后才决定下一条；`SHOWN` 不等中间回包，但会走冷却和重试 | 本地按 `countMode` 计数，立即选择 ready 实例展示下一条 |
| 整轮结束 | `SHOWN` 等最后一条确认，`COMPLETED` 等最后一次完成响应 | 前端立即放行；后台异步批量上传 observations/trace，不依赖其回执 |

`/shown`、`/complete`、`/ad-events` 继续服务旧包和其他广告业务，**新入口 v2 不在连播路径调用它们**。新的 observations/trace 上传是单向记录，不是向服务端再次取配置或询问能否展示。

`countMode=SHOWN`：一次 SDK `show()` 被接受，前端本地计数加一。`countMode=COMPLETED`：激励 `onClose.isEnded === true` 才本地计数加一；提前关闭重试当前序号；插屏在有效 `onClose` 后计数。两种模式都只按配置的 `requiredCount` 决定何时放行。不得把 `show()` 调用、`load()` 成功或页面恢复误计为一次展示。

新 v2 入口流程**不调用**每条 `/shown`、`/complete`、`/ad-events` 来决定下一条，也不等待 `/analytics/events` 或诊断上传。将展示/关闭事实放入本地按 `sessionId + adIndex + attemptId` 排序的发送箱；广告播放时或整轮结束后批量异步上传 `POST /app-entry-ad-sessions/:sessionId/observations`，服务端回执只影响“诊断已同步”状态，不影响当前入口放行。上传可多批，不代表多次配置请求。离线时保留有限、加密或最小化的脱敏发送箱，下一次联网后台续传；失败不得触发重复广告。

服务端对 observations 做鉴权、允许广告位校验、事件 ID 幂等与序号去重，保存 `reportedShownCount`、`reportedCompletedCount`、`clientFinishedAt`、`syncStatus`，并在完整序列入库后将 v2 会话标记为“客户端报告完成”，供后台查看。上传失败时保持“待同步”，不能误显示成用户未看完。此数据是**客户端报告的运行记录**，不能冒充 TikTok 平台不可伪造的播放证明。当前代码的其他内容/播放路由未读取 `AppEntryAdSession.completedCount` 作为访问门槛，因此 v2 可以由前端放行；若将来要以入口完成作为服务端权益门槛，必须另设最终服务端确认，那会改变本方案的零等待体验承诺。剧集解锁权益依旧走原有服务器证据校验，不复用 v2 入口计数。

页面重入使用 `launchId + releaseId + sessionId` 的本地状态防重复：记录当前 `adIndex`、计数、尝试 ID、最终完成标记。只在明确收到 SDK 结果后推进；崩溃/宿主重启后的不确定展示不猜测完成。下一次启动可由**新一次配置请求**恢复该会话；当前一次入口广告之间不请求服务器。配置请求失败按原 `onUnavailable` 和已有启动超时策略处理，错误写入诊断，不使用前端广告位自行强弹。

### 3.2 Android 连播状态机

将参考包 `BOOST/FAST` 的以下时序移植到**新入口强弹 v2**，不直接复制测试页的 `beforeunload` 挽留、插屏叠层和自动 20 条目标。服务端 `requiredCount` 仍是唯一目标次数。

```text
CONFIG_RECEIVED -> FIRST_LOADING -> FIRST_READY -> SHOWING(n)
show.accepted(n) -> BACKGROUND_REFILL(next slots)
onClose(n) -> PICK_READY -> show.call(n+1) -> DEFER_REFILL
             -> LOCAL_COUNT -> FINISHED (达到 requiredCount)
```

- 首支先只创建/加载一个实例，避免首屏带宽争用；首支 ready 即补到目标池深。池深初值 6 是**包含 ready、loading 和排队槽的总实例数**，按 app/release 灰度可设 3/4/6；不是 6 个并发 `load()`。同一广告位串行，不同广告位最多各 1 个加载通道。池深及并发受宿主能力、内存与错误率约束。
- 每个槽显式记录 `CREATED/LOADING/READY/SHOWING/CLOSED/FAILED`、实例 ID、广告位、创建/加载/展示时间和一次性消费标记。`pickReady` 优先当前目标位的 ready 槽；目标位无 ready 时可取另一允许位的 ready 槽，按实际广告位上报，不为轮换强制等待。`show()` 只调用一次；失败实例不得再次误用。
- 当前广告播放期间补池；`onClose` 的关键路径只做必要状态转移、释放展示互斥并调度下一条。昂贵的序列化、日志上传、销毁和补池延后到下一条 `show.call` 之后。保持监听器解绑与一次性终态，兼容 `onClose` 早于 `show()` Promise 落定。
- 入口连播使用独立的交接互斥状态。Android 收到前一条可信 `onClose` 后，像参考包一样从 A/B 已就绪池选择下一支并立即调用 `show()`；不经跨广告位固定 300 ms 冷却。双位仍只允许**一个广告处于展示状态**。若真机 SDK 返回 `104111006`/忙碌，退避等待**同一个 ready 槽**并记录原始回调；不把它判成无填充、不新建洪泛实例。其他业务广告仍受全局互斥，入口退出后恢复原有调度。保留按 release 的快速回滚开关。
- 回退备用位取消无条件 650 ms 等待：有 ready 备位就立刻尝试；真实频控/平台互斥按错误类型和 SDK 给出的条件退避，`NO_FILL` 熔断一段时间。没有 ready 时显示可理解的加载态，不以首页闪现伪装连续成功。连续无填充、宿主失活、配置过期时按 `onUnavailable` 结束/阻止，不无限循环。
- iOS 使用一个主位，继续当前兼容加载/直展实验策略；不引入 Android 双位、6 槽池和零冷却快交接。官方 Mini Drama 文档明确规定 `show()` 返回 Promise、`onClose` 可用于完播判断，**没有保证 `load()` 在所有宿主版本可用**，须先能力检测。

参考包默认 Android `BOOST` 还带返回挽留，`STAGE` 有“插屏打底并叠激励”的实验。二者可能打断现有原生互斥和激励完播，不属于本次入口连播实现。官方要求激励广告在用户预期奖励的合适节点展示；目标次数与展示位置还须按 Portal/真机规则验收。**连续展示的目标是移除应用侧不必要等待，不能保证 TikTok 原生广告之间绝对零帧空隙。**

## 4. 彩蛋调试台与原始数据入库

当前 `debugRecords` 仅内存保留 200 条，而且只在彩蛋调试台激活时写入；SDK 回调快照超过约 4096 字符即截断，HTTP 请求/响应也截断。`/analytics/events` 存的是整理后的事件；`/runtime-errors` 默认不落广告诊断，`/ad-events` 默认丢弃 `FAILED`。因此要新增**独立的原始诊断通道**，不要把大 JSON 塞入高频业务表。

定义 `ClientTraceSession`（appKey、releaseId、launchId、sessionId、用户标识、OS/TikTok/SDK 版本、启停时间、采集级别）和 `ClientTraceRecord`（`recordId`、`traceId`、`seq`、设备时钟及单调时钟、`kind`、`phase`、`operationId`、`attemptId`、`adIndex`、`placementId`、`requestId`、结构化 `payload`、`truncated`/`droppedCount`、`receivedAt`）。每个小程序的业务库各建同结构表；唯一键 `traceId + recordId`，索引覆盖 `receivedAt`、`operationId`、`requestId`、`sessionId + seq`。原始快照与整理后的分析列并存，明确标记哪些字段被截断或脱敏。

采集种类：`SDK_CALL`（create/load/show 入参、实例 ID、调用时间）、`SDK_CALLBACK`（onLoad/onError/onClose 原始可枚举及 Error 非枚举属性快照）、`SDK_PROMISE`（resolve/reject）、`HTTP_REQUEST`/`HTTP_RESPONSE`（**本项目** URL/path、方法、允许的头和 JSON 体、状态码、响应头/体、耗时）、`RUNTIME_ERROR`、`ENTRY_STATE`、`TRACE_DROP`。序列化器应处理 `Error.name/message/stack/cause`、循环引用、不可读 getter、BigInt、数组和深度限制；记录采集失败原因。`Authorization`、Cookie、密码、OAuth code、播放 token、签名 URL、用户标识和投放追踪参数在**客户端发送前**按字段脱敏，服务端再脱敏一次。对 JSON/文本设置可配置上限，例如单条 16 KiB、批次 128 KiB；超限必须留下长度与截断原因。不能保存视频二进制、完整 JWT 或未经授权的第三方请求体。

采集级别：常态只保留错误及其前后有限上下文；管理员在后台按 app/release/测试会话开启 24 小时全量调试，彩蛋调试台显示同步状态、待发条数、丢弃条数和可复制 `traceId`。客户端在登录前只缓冲脱敏错误，拿到用户会话后再上传。上传接口 `POST /client-traces/batches` 与入口状态观察接口都使用有界队列、指数退避、幂等批次、超时，不得阻塞 `show()`、关闭回调或页面切换；对上传自身不再递归采集完整 body。后台支持按 app、release、OS、广告位、错误码、`operationId`、`sessionId`、`requestId` 查询时间线并下载脱敏 JSON。原始诊断默认留存 7 天，可按容量调整；摘要指标保留更久。

## 5. 服务端运行日志

当前 Fastify/Pino 已写 stdout，`compose.production.self-hosted.yml` 为 API/worker 配置 `json-file` 50 MiB × 3；但生产关闭默认请求日志，自定义 `onResponse` 对请求抽样、对相同 route/status 的错误采样合并。这解释了“有容器日志，却难以追到某一次完整接口错误”。线上容器是否已经采用本地 compose 的轮转设置，部署前须 `docker inspect` 实测，不能只看仓库配置。

- API：所有 4xx/5xx 及业务关键路由（入口配置、诊断接收、广告事件、奖励确认、播放授权）每次记录结构化摘要：UTC、`requestId`、appKey、releaseId、method、路由模板、status、耗时、数据库耗时、错误 code、异常类型/stack、上游 request ID。2xx 可采样；完整请求/响应体只在授权调试会话里经脱敏入诊断库。不要把 JWT、密钥、播放 token、完整查询串写入 Pino。
- `error-handler.ts` 中 400/409/503 被合并或缺少异常详情的分支补充错误类型和 `requestId`；保留客户端现有错误响应结构。工作进程的每个任务记录 job ID、appKey、阶段、重试次数和上游 request ID；异常带 stack。前端所有 API 请求透传 `X-Request-ID` 响应值并与客户端 `traceId` 关联，服务器生成的请求 ID 始终权威。
- 在 Docker 轮转之外部署日志采集到受限目录/集中日志服务，按服务、容器版本和时间检索，建议保留 14–30 天；配置磁盘配额、访问权限和监控。先通过 `docker logs --since` 与容器 `LogConfig` 验证，避免误以为 stdout 已长期保存。日志采集失败不得影响 API 响应。

## 7. 实施顺序与验收

1. **先上兼容 API 和迁移**：新增表/接口，旧 v0.0.4.1/v0.0.5/v0.0.6 包原样可调用；四包库逐一迁移并只读验证。确认现网容器日志设置，部署结构化错误摘要和采集，后台先能按 `requestId` 查到一条 4xx/5xx。
2. **再出新前端 release**：仅四个目标包的新 release 启用 v2；Android 先以池深 3 小比例真机灰度，再到 4/6；iOS 维持单位。服务端入口 `enabled`、次数、`countMode`、归因及豁免仍从后台控制。任何配置关闭不得触发 SDK `show()`。
3. **功能验收**：`SHOWN`、`COMPLETED` 各测试 1/3/10 次、2 秒内快关、提前关闭、无填充、忙碌、离线、后台恢复、重复 `onClose`、Promise/回调乱序。断言从首条配置返回到最后关闭期间无阻塞的业务 HTTP；`onClose(n)` 后下一条选位和 `show.call(n+1)` 前没有预热、上传、`/shown`、`/complete` 或固定 300/650/1000 ms 定时器。剧集解锁仍必须经过服务端确认。
4. **性能验收**：真机分别记录 `close -> show.call` 和 `close -> show.resolve` 的 P50/P95、首页暴露帧、ready 池命中率、无填充率、`104111006` 与 `50008` 的独立操作率。目标先定 Android ready 命中场景 `close -> show.call` P95 < 100 ms、无应用侧固定等待；原生上屏空窗与旧包对照评估，不宣称绝对 0 ms。若忙碌率、失败率或首页暴露恶化，立即将该 release 的快交接/池深开关回退。
5. **诊断验收**：同一真机故意触发一次 SDK 错误和一次 API 4xx，调试台、trace 表、后台时间线与 Docker/集中日志能按 `traceId/operationId/requestId` 串联。核对错误对象中的主码、子码、消息、来源以及请求/响应；检查令牌和播放授权字段已脱敏，上传中断后补发且不重复入库。连续运行观察 API CPU、DB 连接、表增速和日志磁盘使用。

回滚只关闭**新 release** 的 v2 快交接/深池策略或将其入口 `enabled` 关闭；保留增量表、旧会话和日志，不回滚奖励记录。需明确：配置关闭入口强弹不会关闭独立配置的剧集解锁、退出挽留和剧集插屏。

## 9. 本轮代码实施状态（尚未部署）

本轮已在本地完成以下代码，只有四个目标包的 `*-v006-dual-*` release 会请求 `entryFlowVersion: 2`；API 只在入口策略启用、模式为 `REWARDED_GATED` 时返回 v2。其余 release 沿用 v1 的 `/shown`、`/complete` 和原本的剧集解锁/插屏/挽留链路。

- `entry-ad-flow-v2.ts` 在前端按 `SHOWN`/`COMPLETED` 本地计数，进度按入口会话保留在 sessionStorage；observations 放入有界发送箱异步上报，不等待服务端回执才播放下一条或放行。
- Android 的主备位同时预热，首支 ready 后扩池；同位 `load()` 仍串行，不同位可并行。只对当前入口会话开放原生广告冷却期内的快速交接，SDK 忙碌时短退避并复用已准备的实例。iOS 保持主位单广告位。
- 新增客户端 trace 发送箱、双端脱敏、SDK JS 可见回调/Promise 与本项目 HTTP 请求/响应快照；彩蛋调试台从入口启动阶段开始缓冲记录，不必先打开调试台。页面显示 trace ID、待上传和丢弃数量。后台可按 release、系统、广告位、错误码、操作/请求/会话/trace ID 查询并导出脱敏 JSON。
- API 对每个 4xx/5xx 输出路由模板、`requestId`、业务错误码和耗时；worker 输出结构化任务与异常摘要。生产 stdout 可通过 `docker logs --since 30m <api-container>` 和 `docker logs --since 30m <worker-container>` 查看。仓库当前 API/worker Docker 日志轮转为 50 MiB × 3；更长期的集中归档仍需在线上运维环境配置。
- 新增数据库迁移 `20261110180000_entry_trace_v2`，只对四个目标包的新链路开放 trace/observations。部署前运行 `node dist/scripts/check-v006-schema.js --expect=dramaflicks,heartreel,sweetreel,luxereel`，确认四个隔离库均完成迁移。`node dist/scripts/prune-client-traces.js --expect=dramaflicks,heartreel,sweetreel,luxereel` 先预览 7 天以前的记录；排程时加 `--apply` 才删除。需由运维安排定时执行。

采集边界：TikTok 原生广告的 `show()`/`onError`/`onClose` 不是本项目 HTTP 接口，不能读取 SDK 内部请求包。服务端保存的是小程序 JS 可见原始对象的脱敏快照；单条上限 16 KiB，过长会标记 `truncated`。这能解释此前调试台空白的直接原因：入口广告发生时调试台尚未激活，旧实现直接丢弃启动阶段的内存记录。

本地校验覆盖前端/API 测试、三端 TypeScript 与构建、Prisma schema 校验。尚未执行数据库迁移、服务器部署、集中日志配置和 Android/iOS 真机时序验收；因此不能用本地测试结果宣称原生广告上屏已经零空窗。播放器本轮未修改，需另按播放链路诊断处理。
