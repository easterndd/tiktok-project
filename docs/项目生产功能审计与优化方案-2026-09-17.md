# QuicK ReeLS 项目生产功能审计与优化方案

> 审计日期：2026-09-17
> 审计范围：Mini Web、运营管理后台、Fastify API、Prisma 数据模型、广告链路、数据统计、权限系统、构建与部署配置
> 当前结论：核心框架可以运行，但广告可信闭环、数据统计口径、管理员权限、TikTok 发布和生产运维尚未达到正式生产标准。

## 一、验证结果

本次审计基于当前工作区代码和本地数据库状态完成，已执行以下验证：

- 全仓 TypeScript 类型检查通过。
- API、Mini Web、Admin Web 构建通过。
- 现有 15 个自动化测试全部通过。
- Prisma Schema 校验通过。
- 当前 6 个数据库迁移均已应用。
- 本地 PostgreSQL 容器运行正常。
- TikTok Minis 正式发布检查未通过。

需要注意：测试和构建通过只能证明现有代码能够编译并满足当前测试预期，不代表业务安全和生产闭环已经成立。

## 二、广告功能现状

### 2.1 已实现的广告类型

项目当前包含两类广告代码：

1. 小程序进入广告
   - 支持插屏广告 `INTERSTITIAL`。
   - 支持激励门槛广告 `REWARDED_GATED`。
   - 前端通过 `TTMinis.createInterstitialAd` 或 `TTMinis.createRewardedVideoAd` 拉起广告。
   - 服务端维护进入广告策略、启动会话、完成次数及广告事件。

2. 锁定剧集激励广告
   - 后台可以配置免费集数、广告位和每集所需广告次数。
   - 锁定剧集可以创建奖励会话。
   - 前端通过 `TTMinis.createRewardedVideoAd` 拉起激励广告。
   - 完成配置次数后创建剧集解锁记录。

主要代码位置：

- `apps/mini-web/src/components/EntryAdGate.tsx`
- `apps/mini-web/src/features/ads/app-entry-ad.ts`
- `apps/mini-web/src/features/ads/rewarded-ad.ts`
- `apps/api/src/modules/app-entry-ads/routes.ts`
- `apps/api/src/modules/ads/routes.ts`
- `apps/api/src/modules/episodes/routes.ts`

### 2.2 当前实际运行状态

当前本地环境不会真正播放广告，原因包括：

- 数据库没有进入广告策略记录，系统使用默认关闭策略。
- 当前唯一短剧有 3 集，并且 3 集全部免费，不会触发剧集激励广告。
- 当前剧集没有 `tiktokEpisodeId`。
- 当前剧集没有 `byteplusVid`。
- Mini Web 本地构建没有配置 `VITE_TIKTOK_CLIENT_KEY`。
- 当前构建仍指向本地 API。
- `pnpm --filter mini-web check:release` 检查失败。
- 浏览器环境不具备真实 TikTok Minis 广告和播放器能力，必须通过 TikTok Preview 或正式容器验证。

因此，当前状态应定义为：

> 已存在广告调用和会话管理代码，但尚未形成可以在 TikTok 环境中完成真实播放和正式验收的生产配置。

### 2.3 严重安全问题：激励广告可被绕过

进入广告完成接口会检查相同事件 ID 的 `SHOWN` 记录，完整性相对较好。

但剧集激励广告完成接口目前没有验证：

- 广告是否成功展示。
- 广告是否完整播放。
- 是否存在对应的 `SHOWN` 事件。
- 客户端上报的完成事件是否来自可信平台结果。

客户端只要拥有有效用户 Token 和奖励会话 ID，就可以直接调用完成接口。达到配置次数后，服务端会创建 `EpisodeUnlock`，无需真实观看广告。

这属于生产发布阻断问题，可能造成：

- 广告收益损失。
- 付费内容被绕过。
- 广告完成率和解锁率数据失真。
- 自动化脚本批量解锁内容。

### 2.4 广告系统生产改造

必须完成以下改造：

1. 前端为每次广告生成唯一事件 ID。
2. `SHOWN` 事件和完成请求必须使用同一个事件 ID。
3. 服务端完成奖励前验证：
   - 用户与奖励会话一致。
   - 剧集与奖励会话一致。
   - 广告位与会话配置一致。
   - 广告序号等于当前应完成序号。
   - 存在对应的 `SHOWN` 记录。
   - 事件没有被其他奖励重复使用。
4. 在串行化事务中创建完成记录和剧集解锁。
5. 增加以下测试：
   - 未展示广告不能解锁。
   - 未完整观看不能解锁。
   - 错误广告位不能解锁。
   - 错误用户不能完成其他用户的会话。
   - 重复事件只能计算一次。
   - 并发完成请求不能增加多次计数。
   - 过期会话不能解锁。

## 三、观众数据现状

### 3.1 日期选择现状

后台图表右上角显示的日历图标只是装饰图标，不是日期选择控件。

当前真正可用的筛选只有：

- 近 7 天
- 近 30 天
- 近 90 天

后台会把选择值作为 `days` 参数传给：

- `/admin/analytics/audience`
- `/admin/analytics/playback-quality`

API 只接受 1 至 90 天，不支持：

- 自定义开始日期。
- 自定义结束日期。
- 今日、昨日、本周、上周、本月等快捷范围。
- 业务时区。
- 和前一个周期进行同比或环比。

### 3.2 当前统计口径问题

#### 活跃观众

当前活跃观众是所选周期内存在 `WatchProgress` 更新记录的去重用户数。

问题：

- 只有成功写入进度的用户才会被认为活跃。
- 打开小程序、查看首页、搜索或打开详情页不会计入活跃。
- 无法表示 DAU、WAU、MAU。

#### 新增观众

当前按 `User.createdAt` 统计匿名用户创建数量。

这个口径可以作为新增设备或匿名身份数，但不等同于真实注册用户数。

#### 观看会话

当前“观看会话”实际等于 `WatchProgress` 表记录数。

由于每个用户和每集只有一条唯一进度记录，所以它既不是观看会话数量，也不是进度上报次数。

#### 完播集数

当前按 `WatchProgress.completed = true` 统计。

问题：

- 没有独立的完播发生时间。
- 用户完成后再次更新进度可能改变统计所属日期。
- 无法区分重复完播和首次完播。

#### 每日活跃趋势

当前图表按进度记录更新时间计数，没有按日期去重用户。

因此图表名称“活跃观众事件”比“活跃观众”更接近实际含义，但仍然不是严格的活跃事件流。

#### 收藏、分享和搜索

- 分享和搜索会按所选时间范围过滤。
- 收藏没有按时间范围过滤。
- 切换 7、30、90 天时，收藏数字保持累计总数，和页面其他指标口径不一致。

#### 时区

统计周期先使用服务器本地时间计算，再通过 ISO UTC 日期生成图表键值，存在跨时区日期偏移风险。

#### 播放质量

播放质量查询最多读取最新 10,000 条事件后在 Node.js 内存中聚合。数据超过 10,000 条后，页面仍显示结果，但它已不再代表完整周期。

### 3.3 当前本地数据说明

审计时本地数据库状态：

- 用户数：3
- 观看进度：0
- 广告事件：0
- 剧集解锁：0
- 播放质量事件：0
- 搜索事件：1

因此后台出现“新增观众 3、活跃观众 0、观看会话 0”与当前数据库状态一致。

### 3.4 数据统计生产改造

建议新增独立事件模型：

1. `AppSession`
   - 用户打开小程序时创建。
   - 记录启动时间、结束时间、平台版本、客户端版本和来源。

2. `PlaybackSession`
   - 每次开始播放创建独立会话。
   - 记录首帧、暂停、缓冲、退出和播放时长。

3. `EpisodeCompletionEvent`
   - 首次完播单独记录。
   - 与当前播放进度状态分离。

4. `AudienceActivityEvent`
   - 可记录进入首页、详情页、搜索和播放等关键活跃行为。

API 改为明确日期范围：

```text
GET /admin/analytics/audience?from=2026-09-01&to=2026-09-17&timezone=Asia/Shanghai
```

统计应统一使用半开区间：

```text
[from, to)
```

数据库层应直接完成：

- `COUNT(DISTINCT userId)`
- 按业务时区分组
- DAU、WAU、MAU
- 新增用户
- 播放会话
- 首次完播
- 收藏、分享、搜索
- 广告请求、展示、完成、失败

数据量增加后，应建立每日汇总表或物化视图，避免后台每次读取大量明细事件。

## 四、页面组件开关同步现状

### 4.1 已同步的组件

当前 7 个开关已经和 Mini Web 对应组件绑定：

| 开关 | 前端效果 |
| --- | --- |
| `APP_TOPBAR` | 控制顶部导航 |
| `APP_BOTTOM_NAV` | 控制底部导航 |
| `HOME_INTRO` | 控制首页介绍区 |
| `HOME_FEED` | 控制首页内容流 |
| `ALBUM_DESCRIPTION` | 控制剧集简介 |
| `PROFILE_HISTORY` | 控制观看历史 |
| `PROFILE_FAVORITES` | 控制收藏列表 |

后台通过 `/admin/ui-components/:key` 保存到数据库，小程序通过 `/ui-components` 读取。

当前数据库中 7 个开关全部开启。

### 4.2 当前同步限制

虽然功能已经连接，但还不是严格意义上的实时配置系统：

- 前端缓存配置 15 秒。
- 已经打开的页面不会收到服务端主动通知。
- API 请求失败时会回退到默认配置，并默认全部开启。
- 这可能导致运营人员已经关闭的模块在故障时重新显示。
- 后台保存后只更新本地状态，没有再次读取服务端确认最终结果。
- `config` 字段可以保存，但后台没有配置编辑器，前端也没有实际消费。
- 没有配置草稿。
- 没有预览环境。
- 没有发布动作。
- 没有版本号和配置回滚。
- 没有多人同时修改时的冲突检测。
- 管理端接口会合并默认项，公共接口在数据库存在部分记录时不会补齐缺失默认项，两边行为不完全一致。

### 4.3 组件配置生产改造

建议增加配置发布模型：

```text
UiConfigVersion
- id
- version
- status: DRAFT | PUBLISHED | ROLLED_BACK
- content
- createdBy
- createdAt
- publishedAt
```

推荐流程：

1. 运营人员修改草稿。
2. 后台展示 Mini Web 预览。
3. 点击发布后生成新版本。
4. Mini Web 拉取已发布版本。
5. API 返回 `version` 和 `ETag`。
6. 发布后主动使 CDN 或前端缓存失效。
7. 故障时继续使用客户端最后一次成功配置，而不是默认全部开启。
8. 支持一键回滚到上一版本。

## 五、运营管理员现状

### 5.1 当前已有能力

- 管理员邮箱和密码登录。
- 密码使用哈希保存。
- 登录后签发管理员 JWT。
- 用户 Token 和管理员 Token 已做类型隔离。
- 大部分后台写操作会创建审计日志。
- 数据库中存在管理员角色字段。

### 5.2 当前未实现功能

后台侧边栏中的“运营管理员”和头像 `OP` 是静态文本，并不来自当前登录用户。

当前尚未实现：

- 当前登录管理员信息接口。
- 管理员列表。
- 创建和邀请管理员。
- 禁用或删除管理员。
- 修改密码。
- 忘记密码。
- 密码重置。
- 多因素认证。
- 登录设备和会话管理。
- 强制下线。
- Token 撤销。
- 审计日志查看页面。
- 按角色控制后台菜单。
- 按角色控制 API。
- 登录失败锁定。
- 管理员登录专用限流。

### 5.3 RBAC 问题

数据库虽然有 `AdminUser.role`，登录 Token 也包含角色，但 `requireAdmin` 只检查 Token 类型是否为管理员。

因此当前：

- `OWNER`
- `EDITOR`
- 未来可能增加的 `ANALYST`

拥有完全相同的 API 权限。

建议权限划分：

| 角色 | 建议权限 |
| --- | --- |
| `OWNER` | 管理员管理、权限、安全设置、全部内容和广告配置 |
| `EDITOR` | 内容创建、剧集管理、上传、页面配置 |
| `ANALYST` | 只读访问观众、广告、播放质量和收入数据 |
| `SUPPORT` | 只读用户状态和问题诊断，不允许修改内容 |

服务端应使用明确权限中间件：

```text
requirePermission("content.write")
requirePermission("ads.manage")
requirePermission("analytics.read")
requirePermission("admins.manage")
```

不能只依赖前端隐藏菜单。

## 七、其他生产风险

### 7.1 密钥管理

本机 API `.env` 中存在真实风格的 TikTok、BytePlus 和管理员凭据。

文件虽然已被 `.gitignore` 排除，但仍建议：

- 立即轮换已有凭据。
- 使用云密钥管理、Docker Secret 或受控运行时环境变量。
- 管理员首次创建后删除 Bootstrap 密码。
- 不在开发机长期保存生产密钥。
- CI 中增加密钥扫描。

### 7.2 健康检查

当前 `/health` 在数据库不可用时仍返回 HTTP 200，只在响应体中标记 `degraded`。

Docker 健康检查只判断 HTTP 是否成功，因此数据库故障时容器仍可能被判断为健康。

建议拆分：

- `/live`：进程存活即可返回 200。
- `/ready`：数据库、必要配置和依赖可用时才返回 200，否则返回 503。

### 7.3 数据分页

多个后台接口直接返回全部专辑、全部剧集或大量记录，没有完整分页机制。

随着数据增长会导致：

- 后台首次加载越来越慢。
- 统计周期变化时重复加载无关数据。
- API 内存和数据库压力增加。
- 管理页面无法快速搜索和筛选。

### 7.4 静态资源存储

封面支持保存到本地磁盘，但部分生产 Compose 配置没有为封面目录挂载持久卷。

容器重建或迁移后存在封面丢失风险。生产环境应使用 COS、S3 或其他对象存储，并通过 CDN 分发。

### 7.5 正式构建

当前 Mini Web 构建：

- 会生成 Source Map。
- 当前本地构建包含 localhost API 地址。
- 正式发布检查未通过。

正式环境应：

- 关闭公开 Source Map，或只上传到内部错误监控。
- CI 强制执行 `build:minis:release` 和 `check:release`。
- 禁止包含 localhost、Mock 模式和占位凭据的包发布。
- 对 TikTok Client Key、API HTTPS 地址和 Minis 配置进行自动检查。

### 7.6 监控和告警

当前缺少完整的生产可观测性：

- 应用指标。
- 分布式追踪。
- 错误聚合。
- 广告失败率告警。
- 播放错误率告警。
- Worker 队列积压告警。
- 数据库连接和慢查询告警。
- 配置发布失败告警。

## 十、生产验收标准

项目正式发布前，至少应满足：

- 未真实展示广告时无法完成剧集解锁。
- 广告事件不能重复计数。
- 进入广告和剧集广告可在 TikTok Preview 真机成功播放。
- 锁定剧集只能在满足访问策略后播放。
- 所有观众指标有清晰且一致的统计定义。
- 自定义日期范围按指定时区正确返回数据。
